1. O QUE É O CONTRATEMPO
================================================================================

Um MARKETPLACE de colecionáveis: action figures, cartas, HQs, vinis,
videogames, itens retrô e de cultura geek.

"Marketplace" quer dizer que a loja não vende nada sozinha: ela conecta
pessoas. Qualquer usuário cadastrado pode:
  - COMPRAR de outros usuários (carrinho, checkout, frete, pedidos);
  - VENDER os próprios itens (anúncios com fotos, estoque, vendas).

Uma mesma conta compra e vende; não existem "tipos" separados de conta.

A equipe do site (administradores) cuida do catálogo (categorias e
franquias), do frete, das perguntas frequentes, das mensagens de contato e
das denúncias, pelo painel /admin/.

3. COMO O DJANGO FUNCIONA (O CAMINHO DE UMA PÁGINA)
================================================================================

Django segue o padrão MVT (Model – View – Template). Quando alguém abre,
por exemplo, http://127.0.0.1:8000/produtos/4/ acontece isto:

  1. NAVEGADOR pede o endereço /produtos/4/ ao servidor.

  2. MIDDLEWARES (filtros que rodam em toda requisição): leem o cookie de
     sessão para saber quem está logado (request.user), protegem contra
     CSRF, preparam as mensagens de aviso etc.

  3. URLS (marketplace/urls.py): a lista de endereços. O Django acha a
     linha  path("produtos/<int:produto_id>/", views.produto_detalhe)
     e chama a função produto_detalhe com produto_id=4.

  4. VIEW (marketplace/views.py): a função que contém a lógica. Ela pede ao
     banco o produto 4, as fotos, as avaliações, as perguntas, calcula o
     frete etc.

  5. MODEL (marketplace/models.py): cada classe representa uma tabela. A
     view escreve  Produto.objects.get(pk=4)  e o Django gera o SQL
     (SELECT ... FROM produtos WHERE id = 4) sozinho. Isso é o ORM.

  6. TEMPLATE (templates/produto.html): HTML com "buracos" que o Django
     preenche:  {{ produto.nome }},  {% for imagem in imagens %} ... etc.
     Todos os templates "estendem" o base.html (cabeçalho, rodapé,
     mensagens), então cada página só escreve o próprio miolo.

  7. CONTEXT PROCESSORS (marketplace/context_processors.py): dados que
     TODAS as páginas recebem automaticamente — as categorias do menu e o
     número de itens do carrinho (a bolinha no ícone).

  8. RESPOSTA: o HTML pronto volta ao navegador, que baixa o CSS, o
     JavaScript e as imagens (arquivos "estáticos" e "media").

Outros conceitos que aparecem no projeto:

  - SESSÃO: o Django guarda no banco (tabela django_session) quem está
    logado e as escolhas do checkout. O navegador só guarda um cookie com
    um código (sessionid).
  - MESSAGES: os avisos coloridos no topo ("Anúncio publicado", "Senha
    incorreta"...). A view registra a mensagem e a próxima página exibe.
  - FORMS (forms.py): classes que desenham os campos e VALIDAM o que o
    usuário digitou (CEP com 8 dígitos, senha forte, preço > 0...).
  - POST x GET: GET só lê (abrir página). POST altera dados (salvar,
    excluir, comprar). Toda ação que altera dados neste projeto é POST.
  - @login_required: "etiqueta" colocada nas views que exigem login; quem
    não está logado é levado à página de login e volta depois (?next=).
  - MIGRATIONS: arquivos que descrevem mudanças no banco. O comando
    "python manage.py migrate" aplica o que falta.

5. CONFIGURAÇÃO (.env E settings.py)
================================================================================

O settings.py NÃO tem senhas escritas. Ele lê o arquivo .env (na raiz do
projeto), que cada máquina tem o seu.

Variáveis do .env:

  DJANGO_DEBUG ........... 1 = desenvolvimento (seu computador)
                           0 = produção (site publicado)
  DJANGO_ALLOWED_HOSTS ... domínio do site publicado
                           (ex.: enaldo.pythonanywhere.com)
  DJANGO_SECRET_KEY ...... chave secreta usada para assinar cookies e
                           links; obrigatória em produção
  DB_ENGINE .............. mysql  ou  sqlite
  DB_NAME, DB_USER, DB_PASSWORD, DB_HOST, DB_PORT
                           dados de conexão do MySQL
  EMAIL_HOST_USER ........ conta Gmail que envia os e-mails
  EMAIL_HOST_PASSWORD .... SENHA DE APP do Gmail (16 letras), não a senha
                           normal. Vazio = e-mails aparecem no terminal.

Diferenças entre os modos:

  DESENVOLVIMENTO (DEBUG=1)            PRODUÇÃO (DEBUG=0)
  - erros mostram a tela técnica       - erros mostram as páginas 404/500
    amarela do Django                    bonitas do site
  - o próprio Django serve CSS e fotos - o servidor web serve /static/ e
                                         /media/ (configurado no PythonAnywhere)
  - aceita só localhost                - aceita só o domínio configurado
                                       - cookies só por HTTPS
                                       - não inicia sem DJANGO_SECRET_KEY

Outras configurações importantes no settings.py:
  - AUTH_USER_MODEL = "marketplace.Usuario"  (usuário personalizado, login
    por e-mail)
  - LANGUAGE_CODE "pt-br" e fuso "America/Sao_Paulo"
  - MEDIA_ROOT = contratempo/media (onde as fotos são gravadas)
  - PASSWORD_RESET_TIMEOUT = 3 dias (validade dos links por e-mail)
  - LOGGING: mostra no terminal os erros de envio de e-mail

6. BANCO DE DADOS (TODAS AS TABELAS)
================================================================================

São 26 tabelas: 17 do marketplace + 9 internas do Django.
(O script MySQL ainda cria 2 "views" SQL de consulta: vw_produtos_ativos e
vw_pedidos_resumo.)

Cada classe em models.py = uma tabela. Nome da classe -> nome da tabela
(definido em  class Meta: db_table = "...").

--------------------------------------------------------------------------------
6.1  USUÁRIOS E DADOS PESSOAIS
--------------------------------------------------------------------------------

[usuarios]  — model Usuario
  Substitui o usuário padrão do Django. O LOGIN É PELO E-MAIL.
  id ................. número do usuário
  nome_completo ...... nome
  email .............. único; sempre gravado em minúsculas
  senha .............. HASH da senha (nunca a senha em texto). No Python o
                       campo se chama "password" (exigência do Django) e é
                       ligado à coluna "senha" por db_column.
                       Formato: pbkdf2_sha256$iterações$sal$hash
  data_nascimento, telefone ... opcionais
  avatar ............. endereço da foto de perfil (/media/avatares/...)
  data_cadastro, data_atualizacao ... preenchidas automaticamente
  status_conta ....... ativo / inativo / suspenso (regra de negócio; conta
                       suspensa não entra)
  is_active .......... se pode fazer login (desativar conta = False)
  is_staff ........... pode entrar no /admin/
  is_superuser ....... tem todas as permissões
  email_confirmado ... conta nova criada pelo site começa em False até
                       clicar no link do e-mail
  last_login ......... último login (preenchido pelo Django)

  Desativar conta é um "soft delete": o usuário nunca é apagado de verdade,
  para não perder o histórico de pedidos e vendas.

[enderecos]  — model Endereco
  Vários por usuário. nome_endereco (Casa, Trabalho), cep, logradouro,
  numero, complemento, bairro, cidade, estado (UF), pais, endereco_principal.
  Só um é principal por usuário (o código garante).
  Se o usuário for apagado, os endereços vão junto (CASCADE).

[formas_pagamento]  — model FormaPagamento
  tipo (crédito, débito, PIX, boleto, outro), apelido, bandeira,
  ultimos_digitos, principal, token_externo.
  NUNCA guarda o número completo, validade ou CVV do cartão.
  token_externo: reservado para quando houver um gateway de pagamento.

--------------------------------------------------------------------------------
6.2  CATÁLOGO
--------------------------------------------------------------------------------

[categorias] e [franquias]  — models Categoria e Franquia
  nome (único), slug (versão para URL: "video-games"), descricao, ativo.
  Cadastradas pela equipe no /admin/.

[produtos]  — model Produto (= o ANÚNCIO)
  vendedor_id ....... quem anuncia                    (PROTECT)
  categoria_id ...... obrigatória                     (PROTECT)
  franquia_id ....... opcional                        (SET_NULL)
  nome, descricao, preco (decimal 10,2)
  quantidade_disponivel ... estoque
  condicao .......... novo / usado / semi-novo
  marca, ano, sku (código interno; único, mas pode ficar vazio)
  status_anuncio .... ativo / pausado / vendido / encerrado
  data_criacao, data_atualizacao

  Status do anúncio:
    ativo ...... aparece na loja e pode ser comprado
    pausado .... escondido temporariamente pelo vendedor
    vendido .... estoque zerou (o SISTEMA define sozinho)
    encerrado .. retirado da loja pelo vendedor ou por denúncia procedente

[produto_imagens]  — model ProdutoImagem
  produto_id, url_imagem (/media/produtos/<id>/<código>.png), principal,
  ordem_exibicao. Só uma principal por produto (o model garante).
  Apagar o produto apaga as imagens (CASCADE).

--------------------------------------------------------------------------------
6.3  CARRINHO
--------------------------------------------------------------------------------

[carrinhos]  — model Carrinho
  usuario_id, status (ativo / finalizado / abandonado).
  O carrinho fica NO BANCO (não no navegador), então aparece em qualquer
  computador em que a pessoa entrar. Cada usuário tem no máximo UM carrinho
  ativo — no MySQL isso é garantido por uma coluna calculada
  (usuario_carrinho_ativo) com índice UNIQUE. Ao comprar, ele vira
  "finalizado" e um novo é criado na próxima vez.

[itens_carrinho]  — model ItemCarrinho
  carrinho_id, produto_id, quantidade, preco_unitario.
  unique_together (carrinho, produto): o mesmo produto não se repete;
  adicionar de novo soma a quantidade.

--------------------------------------------------------------------------------
6.4  PEDIDOS
--------------------------------------------------------------------------------

[pedidos]  — model Pedido
  usuario_id ............ o COMPRADOR                     (PROTECT)
  vendedor_id ........... o VENDEDOR daquele pedido       (PROTECT)
  endereco_id, forma_pagamento_id ... ligação opcional    (SET_NULL)
  endereco_snapshot ..... CÓPIA em texto do endereço usado
  forma_pagamento_snapshot  CÓPIA da forma de pagamento usada
  status_pedido ......... ver tabela abaixo
  valor_total ........... produtos + frete
  valor_frete ........... frete deste pedido
  prazo_entrega_dias .... prazo prometido (dias úteis após o envio)
  codigo_rastreio, data_envio ... preenchidos quando o vendedor envia
  data_criacao, data_atualizacao

  Uma compra com produtos de 3 vendedores gera 3 PEDIDOS — cada vendedor
  envia o seu pacote, cobra o seu frete e atualiza o seu status.

  Status do pedido e quem muda:
    aguardando_pagamento  -> criado no checkout
    pagamento_aprovado    -> o VENDEDOR marca
    processamento         -> o VENDEDOR marca ("em preparação")
    enviado               -> o VENDEDOR marca, informando o rastreio
    entregue              -> o COMPRADOR confirma o recebimento
    cancelado             -> o comprador (só enquanto aguarda pagamento)
                             ou o vendedor (antes de enviar)

[itens_pedido]  — model ItemPedido
  pedido_id (PROTECT), produto_id (SET_NULL), nome_produto,
  preco_unitario, quantidade, subtotal.
  Nome e preço são COPIADOS no momento da compra: se o vendedor mudar o
  preço ou apagar o anúncio depois, o pedido antigo não muda.

--------------------------------------------------------------------------------
6.5  PÓS-VENDA E ATENDIMENTO
--------------------------------------------------------------------------------

[avaliacoes]  — model Avaliacao
  usuario_id, produto_id, pedido_id, nota (1 a 5), comentario,
  status (publicada / oculta / removida — moderação).
  Uma avaliação por produto por compra (unique_together).
  Só avalia quem comprou E recebeu (regra no método clean()).

[perguntas_produto]  — model PerguntaProduto
  produto_id, usuario_id (quem perguntou), pergunta, resposta (vazia =
  sem resposta), status (publicada / oculta), data_pergunta, data_resposta.

[denuncias]  — model Denuncia
  produto_id, usuario_id (quem denunciou), motivo (falsificado, proibido,
  enganoso, golpe, ofensivo, outro), descricao, status (pendente /
  procedente / improcedente), data_denuncia, data_analise.

[contatos]  — model Contato
  Mensagens do formulário de contato: nome, email, assunto, mensagem,
  status (pendente / respondido / arquivado). usuario_id é opcional
  (visitantes também escrevem).

--------------------------------------------------------------------------------
6.6  FRETE E AJUDA
--------------------------------------------------------------------------------

[tabela_frete]  — model TabelaFrete
  uf (única), regiao, valor, prazo_dias, ativo. Uma linha por estado
  (27). ativo = False -> "ainda não entregamos nesse estado".

[perguntas_frequentes]  — model PerguntaFrequente
  tema (conta, compras, entrega, vendas, segurança), pergunta, resposta,
  ordem, ativo. É o conteúdo da página "Dúvidas frequentes".

--------------------------------------------------------------------------------
6.7  COMO AS TABELAS SE LIGAM
--------------------------------------------------------------------------------

  usuarios ─┬─< enderecos
            ├─< formas_pagamento
            ├─< produtos >── categorias
            │      │     >── franquias (opcional)
            │      ├─< produto_imagens
            │      ├─< perguntas_produto
            │      └─< denuncias
            ├─< carrinhos ─< itens_carrinho >── produtos
            ├─< pedidos (como comprador) ─< itens_pedido >── produtos
            ├─< pedidos (como vendedor)
            ├─< avaliacoes >── produtos, pedidos
            └─< contatos (opcional)

  ─<  = "um para muitos" (um usuário tem muitos endereços).
  >── = chave estrangeira (FOREIGN KEY) apontando para outra tabela.

Regras de exclusão (on_delete), e o porquê:
  PROTECT .. impede apagar se houver dependentes. Usado em tudo que é
             DINHEIRO e HISTÓRICO: não se apaga usuário com pedidos ou
             anúncios, nem categoria em uso.
  CASCADE .. apaga junto. Usado em dados AUXILIARES: endereços do usuário,
             fotos do produto, itens do carrinho.
  SET_NULL . só desliga a referência. Usado em ligações OPCIONAIS: franquia
             do produto, endereço do pedido (o snapshot preserva o texto).

7. TIPOS DE USUÁRIO
================================================================================

  VISITANTE (sem login)
    Vê a loja: home, catálogo, busca, produtos, perfis de vendedores,
    categorias, FAQ, contato, sobre, privacidade. Calcula frete.
    Não compra, não pergunta, não denuncia.

  USUÁRIO LOGADO (comprador e vendedor ao mesmo tempo)
    Tudo do visitante +
    Comprar: carrinho, checkout, meus pedidos, avaliar, cancelar.
    Vender: anúncios, estoque, minhas vendas, responder perguntas.
    Conta: dados pessoais, foto, senha, endereços, formas de pagamento.

  ADMINISTRADOR (is_staff / is_superuser)
    Tudo acima + painel /admin/.

9. FLUXOS PASSO A PASSO
================================================================================

9.1 CADASTRO E CONFIRMAÇÃO DE E-MAIL
  1. A pessoa preenche /cadastro/. O formulário valida e-mail repetido,
     senhas iguais e senha forte (validadores do Django: mínimo 8
     caracteres, não só números, não comum, não parecida com nome/e-mail).
  2. A conta é criada com email_confirmado = False e SEM login.
  3. emails.enviar_confirmacao_cadastro() manda um link com um TOKEN
     assinado (vale 3 dias e uma única vez).
  4. O clique abre /cadastro/confirmar/... -> email_confirmado = True ->
     login automático -> "Minha conta".
  5. Antes de confirmar, o login é recusado com o botão "Reenviar link".

9.2 LOGIN
  Busca o usuário pelo e-mail, compara o hash da senha, recusa se o
  e-mail não foi confirmado ou se a conta está suspensa. Sem "Lembrar de
  mim", a sessão acaba ao fechar o navegador. Volta à página de origem
  (?next=), mas só se for do próprio site.

9.3 RECUPERAR SENHA
  Usa o sistema pronto do Django com telas e e-mail próprios: informa o
  e-mail -> recebe link (3 dias, uso único) -> define nova senha. A
  mensagem é a mesma exista ou não a conta (para não revelar e-mails
  cadastrados). Redefinir também confirma o e-mail.

9.4 COMPRA
  1. Produto -> "Adicionar ao carrinho" (ou "Comprar agora", que já vai
     ao checkout). Não deixa passar do estoque nem comprar o próprio
     anúncio.
  2. Carrinho -> confere preço e disponibilidade de novo.
  3. Checkout 1: endereço (guardado na SESSÃO). Calcula o frete.
  4. Checkout 2: forma de pagamento (guardada na sessão).
  5. Checkout 3: revisão -> "Confirmar pedido".
  6. Dentro de uma TRANSAÇÃO (tudo ou nada):
       - trava os produtos no banco (select_for_update), para duas pessoas
         não comprarem a última unidade ao mesmo tempo;
       - confere de novo status e estoque;
       - cria 1 pedido por vendedor (com frete e prazo) e os itens;
       - baixa o estoque; estoque 0 -> anúncio "vendido";
       - finaliza o carrinho.
     Se qualquer coisa falhar, nada é gravado.
  7. E-mails: resumo para o comprador e "Nova venda" para cada vendedor.

9.5 VIDA DE UM PEDIDO
  Vendedor em /vendas/<id>/:
    Aprovar pagamento -> Em preparação -> Enviar (exige código de
    rastreio). A cada etapa o comprador recebe um e-mail.
    Proteção contra clique duplo: o formulário informa de qual status
    partiu; se já mudou, nada acontece.
  Comprador em /conta/pedidos/<id>/:
    "Confirmar recebimento" (só depois de enviado) -> "entregue" ->
    libera "Avaliar produto".
  Cancelar:
    comprador: só enquanto "aguardando pagamento";
    vendedor: até "em preparação".
    O estoque volta (e "vendido" volta a "ativo"); a outra parte recebe
    e-mail.

9.6 VENDA (ANÚNCIO)
  1. "Anunciar" -> preenche o formulário e envia fotos.
  2. As fotos vão para media/produtos/<id>/ com nome aleatório; a primeira
     vira a principal.
  3. Pausar / reativar / encerrar a qualquer momento. Reativar exige
     estoque.
  4. Excluir só é permitido se nunca vendeu (para não quebrar pedidos).
  5. Estoque em lote: zerar um anúncio ativo -> "vendido"; repor estoque
     de um "vendido" -> volta a "ativo".

9.7 PERGUNTAS AO VENDEDOR
  Comprador pergunta (5 a 500 caracteres; não duplica) -> vendedor
  recebe e-mail -> responde no produto ou em "Perguntas recebidas" ->
  comprador recebe e-mail -> resposta fica pública no anúncio.

9.8 AVALIAÇÃO
  Só depois de "entregue", uma vez por produto por pedido, nota de 1 a 5
  + comentário opcional. Entra na nota do produto e do vendedor.

9.9 DENÚNCIA
  Usuário logado (não o dono) escolhe o motivo ("outro" exige descrição
  de 10+ caracteres). Uma denúncia pendente por pessoa por anúncio. No
  /admin/ > Denúncias, a equipe seleciona e aplica:
    "Procedente" -> anúncio encerrado + todas as denúncias dele resolvidas
    "Improcedente" -> só arquiva.
  O vendedor nunca sabe quem denunciou.

9.10 DESATIVAR CONTA
  Exige pausar/encerrar os anúncios ativos antes. A conta é desativada
  (não apagada) e o histórico permanece.

10. REGRAS DE NEGÓCIO (RESUMO)
================================================================================

  - Login por e-mail; e-mail único e em minúsculas.
  - Conta nova só entra depois de confirmar o e-mail.
  - Ninguém compra, pergunta ou denuncia o próprio anúncio.
  - Carrinho nunca passa do estoque disponível.
  - O preço do carrinho acompanha o preço atual do anúncio.
  - Uma compra = um pedido por vendedor; frete cobrado por vendedor.
  - Pedido guarda cópia de endereço, pagamento, nome e preço (snapshots).
  - Estoque 0 -> "vendido"; repor -> "ativo"; cancelar devolve estoque.
  - Anúncio ativo precisa de pelo menos 1 unidade; preço > 0.
  - Até 8 fotos por anúncio, 5 MB cada.
  - Anúncio com vendas não pode ser excluído (só encerrado).
  - Só avalia quem recebeu; uma avaliação por produto por pedido.
  - Endereços: um principal; apagar o principal promove outro.
  - Formas de pagamento: idem; cartão exige bandeira e 4 dígitos.
  - CEP com 8 dígitos; UF com 2 letras.
  - Conta só é desativada sem anúncios ativos; usuário nunca é apagado.

      Sudeste R$ 19,90 (5 dias)     Sul R$ 24,90 (7 dias)

  - Prazo em dias úteis, contado a partir do envio.

12. BUSCA  (marketplace/busca.py)

  - Só anúncios ativos.
  - Sugestões ao digitar (2+ letras): até 6 produtos e 3 categorias;
    setas, Enter e Esc funcionam (main.js).

16. SEGURANÇA
================================================================================

  - Senhas com hash PBKDF2 (o Django nunca guarda a senha).
  - Validação de senha forte no cadastro e na troca.
  - Cartões: só bandeira e 4 últimos dígitos.
  - CSRF: todo formulário tem um código secreto ({% csrf_token %}) que
    impede outros sites de enviarem formulários em nome do usuário.
  - Ações que alteram dados só por POST, e destrutivas com confirmação.
  - Cada pessoa só acessa os próprios pedidos, anúncios, endereços e
    vendas (as views filtram pelo usuário logado; tentativas dão 404).
  - Redirecionamentos (?next=) só para o próprio site.
  - Links de e-mail assinados, com validade e uso único.
  - Reenvio de confirmação limitado (1 por minuto) e mensagens que não
    revelam quais e-mails existem.
  - Uploads: só imagens, até 5 MB, salvas com nome aleatório.
  - Senhas e chaves fora do código (.env), e .env fora do GitHub.
  - Produção: cookies só por HTTPS, domínio restrito, chave obrigatória;
    "python manage.py check --deploy" sem problemas.
  - Dados pessoais (dados.json, .zip, banco SQLite, fotos) fora do GitHub.

17. INSTALAÇÃO, SCRIPTS E COMANDOS
================================================================================

NUMA MÁQUINA NOVA (Windows):
  1. Instalar Python 3.10+ (marcar "Add python.exe to PATH").
     MySQL é opcional.
  2. Copiar a pasta do projeto (sem venv e sem .env) ou clonar do GitHub.
  3. Dois cliques em instalar.bat: cria a venv, instala os pacotes,
     pergunta MySQL ou SQLite, cria o .env e o banco, aplica as migrations,
     carrega banco/dados.json (no SQLite) e oferece criar um administrador.
  4. Dois cliques em rodar.bat: atualiza o banco e abre
     http://127.0.0.1:8000

COMANDOS (dentro da pasta contratempo, com a venv ativa):
  python manage.py runserver ............... liga o site
  python manage.py migrate ................. aplica mudanças no banco
  python manage.py makemigrations .......... cria migration após mudar models
  python manage.py createsuperuser ......... cria administrador
  python manage.py changepassword email .... troca a senha de alguém
  python manage.py testar_email email ...... testa o e-mail
  python manage.py check --deploy .......... confere segurança de produção
  python manage.py collectstatic ........... reúne CSS/JS (produção)

EXPORTAR / IMPORTAR DADOS (na raiz do projeto):
  venv\Scripts\python.exe -X utf8 contratempo\manage.py dumpdata
     --natural-foreign --indent 1 --exclude contenttypes
     --exclude auth.permission --exclude admin.logentry
     --exclude sessions -o banco\dados.json          (tudo numa linha)
  python -X utf8 manage.py loaddata ../banco/dados.json

20. GLOSSÁRIO
================================================================================

  App ............... parte de um projeto Django (aqui: marketplace)
  Model ............. classe Python que representa uma tabela
  View .............. função que processa a requisição e devolve a página
  Template .......... HTML com marcações do Django ({{ }}, {% %})
  ORM ............... tradução automática de Python para SQL
  Migration ......... arquivo que descreve uma mudança no banco
  QuerySet .......... consulta ao banco (ex.: Produto.objects.filter(...))
  Chave estrangeira . coluna que aponta para outra tabela (FOREIGN KEY)
  Snapshot .......... cópia de um dado no momento (endereço no pedido)
  Soft delete ....... "apagar" marcando como inativo, sem remover
  Transação ......... grupo de operações "tudo ou nada"
  Slug .............. versão do nome para URL ("video-games")
  Hash .............. resultado irreversível de uma senha
  Token ............. código secreto temporário (links de e-mail)
  Sessão ............ memória do servidor sobre um visitante
  CSRF .............. ataque de formulário forjado (o Django bloqueia)
  Static ............ arquivos fixos do site (CSS, JS, ícones)
  Media ............. arquivos enviados pelos usuários (fotos)
  venv .............. ambiente Python isolado do projeto
  .env .............. arquivo de configurações secretas da máquina
  WSGI .............. ponte entre o servidor web e o Django
  SMTP .............. protocolo de envio de e-mail
  JSON .............. formato de dados em texto (sugestões, dados.json)
  Deploy ............ publicar o site na internet
  Commit / Push ..... salvar uma versão no Git / enviar ao GitHub

21. PERGUNTAS QUE PODEM APARECER NA APRESENTAÇÃO
================================================================================

P: Por que um usuário personalizado em vez do padrão do Django?
R: Para o login ser por e-mail (o padrão usa "username") e para ter os
   campos do projeto (telefone, avatar, status, e-mail confirmado).

P: Por que copiar endereço e preço no pedido (snapshot)?
R: Para o histórico não mudar. Se o cliente apagar o endereço ou o
   vendedor mudar o preço, o pedido continua mostrando o que valeu na
   compra.

P: O que impede duas pessoas de comprarem a última unidade?
R: A compra roda numa transação que trava os produtos (select_for_update)
   e confere o estoque de novo antes de gravar.

P: Por que um pedido por vendedor?
R: Cada vendedor envia um pacote diferente, com frete, prazo, rastreio e
   status próprios.

P: Como as senhas são guardadas?
R: Como hash PBKDF2 com "sal". Nem o administrador consegue ver a senha.

P: Por que PROTECT, CASCADE e SET_NULL?
R: PROTECT para não perder dinheiro/histórico; CASCADE para dados que só
   existem por causa do dono; SET_NULL para ligações opcionais.

P: Como funciona a busca sem acento?
R: No MySQL a collation já ignora acentos; no SQLite o projeto registra
   uma função Python que remove acentos antes de comparar.

P: Como o site funciona sem MySQL?
R: O settings.py lê DB_ENGINE do .env e troca para SQLite. O código é o
   mesmo porque o ORM do Django gera o SQL certo para cada banco.

P: O que acontece se o e-mail falhar?
R: A ação continua (compra, pergunta...). O erro vai para o log com a
   explicação, e o usuário pode pedir o reenvio quando for o caso.

P: Por que o código e os dados ficam separados no GitHub?
R: Senhas (.env) e dados pessoais (dados.json, fotos, banco) nunca vão
   para o repositório — o .gitignore impede.
